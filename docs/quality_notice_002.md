## 一、起报接缝：确认存在，已写入报告，不需要改数据

**现象**：每天的 08:00 和 20:00，PM2.5 的逐小时变化明显大于其他时段。

**原因**：CAMS 全球大气成分预报每天 00 UTC 与 12 UTC 各起报一次，预报时效 5 天，
地面单层场逐小时输出。把连续两次起报拼成一条长序列时，接缝处会从上一轮的后段外推值
切换成新一轮的分析/首报值，两者初始场不同，数值接不上。吉隆坡是 UTC+8，
所以接缝正好落在本地 08:00 与 20:00。

**复算结果**（KL_City，全期）：

| 检验 | 结果 |
|---|---|
| 08/20 的平均 \|ΔPM2.5\| vs 其他时段 | 15.2 vs 4.7 µg/m³，**3.2 倍** |
| 扣掉（月，钟点）气候态后 | 仍为 **3.0 倍** → 不是正常日变化 |
| 20:00 全网同向跳的节点占比 | **79%**，其他时段 45% → 不是局地天气 |
| 其他污染物接缝倍数 | PM10 3.23 / NO2 2.35 / SO2 2.32 / CO 1.88 / O3 1.81 → 全域同步 |
| 20:00 的平均带符号跳变 | **+17.9 µg/m³**，几乎单向朝上 |

**关于"3 小时插值"的假设：不成立。**
CAMS 全球产品对地面单层场本来就是逐小时输出（3 小时是多层廓线的步长）。
数据侧也测了：3 小时块内一阶差分恒定的比例只有 **1.2%**，二阶差分按 `hour % 3`
分组是 6.07 / 4.72 / 6.08（平的），没有周期 3 结构。线性插值会产生完全相反的模式。

**处理**：不修改数据（没有独立参考序列，改不了），在报告里如实声明。

已落地：
- `reports/sec1_data_and_baseline.md` 新增 §2.1.5
- `README.md` 已知局限第 4 条
- `tools/check_run_seam.py` 复现脚本，数字落在 `models/seam_report.json`

**对下游的实际影响**：17:00–19:00 发出的目标，三小时后正好跨过 20:00 接缝，
会多带一份模型在任何输入里都看不到的误差。5 号、6 号解读分时段误差时要知道这件事。

## 二、钟点编码有缺陷：Top-25 里只有 `hour_sin`，没有 `hour_cos`

这是 1 号在核查质检意见时发现的，**不是外部意见，是我们自己的漏洞**。

02 构造的特征表里 `hour_sin`、`hour_cos`、`month_sin`、`month_cos` 四列都有，
但 03 的特征选择按重要性取 Top-25 时，sin 和 cos 高度相关，只留下了一个 `hour_sin`。

后果很具体：**24 个钟点里只有 13 个不同取值，11 组两两同值**：

| 同值对 | sin |
|---|---|
| 00:00 与 12:00 | 0.000 |
| 01:00 与 11:00 | +0.259 |
| 02:00 与 10:00 | +0.500 |
| 03:00 与 09:00 | +0.707 |
| **04:00 与 08:00** | +0.866 |
| 05:00 与 07:00 | +0.966 |
| 13:00 与 23:00 | −0.259 |
| 14:00 与 22:00 | −0.500 |
| 15:00 与 21:00 | −0.707 |
| **16:00 与 20:00** | −0.866 |
| 17:00 与 19:00 | −0.966 |

**只有 06:00 和 18:00 是唯一的**——它们是 sin 的 ±1 极值，不与其他任何钟点撞。
（本通告初稿把这两个当成反例写，写反了，2 号指出后已更正。）

真正要命的是加粗那两行：**两个起报接缝时刻都撞在别的钟点上**。
08:00 与 04:00 同值，20:00 与 16:00 同值。也就是说，模型在最容易出错、
跳变最大的那两个时刻，恰好分不清它们是几点——而 08:00 和 20:00 正是本文第一部分
要声明的接缝时刻。这两件事叠在一起，不是巧合。

**这不是"再加一个特征"的问题，是编码不完整。** `hour_cos` 必须进最终特征表，
`month_cos` 同理（虽然月份在项目里主要靠气候态基线吸收，优先级低一些）。

**并且这件事已经做成机器检查了**，不再靠人眼：
`python tools/check_merge_gate.py --main` 会直接报
`hour_sin/hour_cos 只进了一个（共 25 个特征）`。当前 main 上是 FAIL——也就是说
**这个问题到现在还没有被解决，只是被识别和派了活**。等 3 号推 Q3-1 之后才会变绿。

## 三、邻域格点：增益确认来自邻域，不是钟点（本通告 v1.1 更正）

**更正说明**：本节初稿推测"增益大部分来自补全 `hour_cos`，邻域贡献未知"。
7 号当场把实验拆成四组重跑，结果与这个推测相反，下表是他的数据（验证集）：

| 特征组合 | MAE | Macro-F1 | 平均代价 |
|---|---|---|---|
| 基础 25 特征 | 5.964 | 0.7227 | 0.5687 |
| 只加钟点 | 5.898 | 0.7241 | 0.5682 |
| **只加邻域** | **5.822** | **0.7320** | **0.5331** |
| 两者都加 | 5.764 | 0.7344 | 0.5337 |

结论有三条：

1. **只加钟点几乎没有变化**（MAE −0.066，Macro-F1 +0.0014，代价 −0.0005）。
   补 `hour_cos` 仍然要做——那是修编码缺陷，不是性能手段，别指望它带来提升。
2. **增益基本全部来自邻域格点**（只加邻域就有 MAE −0.142、Macro-F1 +0.0093、代价 −0.0356），
   两者都加只比只加邻域再好一点点。
3. 所以 **5 号的 Q5-2（单独归因）可以取消**，这一条已经被 7 号的四组实验回答掉了。

### 为什么这和 3 号"空间特征没有增益"不矛盾

两条结论都对，因为它们用的不是同一种空间特征：

| | 3 号的消融 | 7 号的实验 |
|---|---|---|
| 形式 | σ=60 km 高斯加权的**上风向平流** | 另外 25 个格点各自的**当前浓度 + 近 3 小时变化**，共 50 列，不做平均 |
| 缺失 | 受体上 8.97%，且用自身 `pm2_5_lag` 填补，退化成了自回归 | 直接用邻点原值 |
| 结果 | 无增益 | MAE −0.142、代价 −0.0356 |

上风向加权把 26 个格点压成 1 个标量，而 50 列原始值保留了每个方向的信息。
**压缩成平均值的做法很可能复现不出这个增益**——这一点对 3 号的实现有直接影响，见 Q3-2。

**邻域特征的定义改了，这一点必须注意。** 本通告初稿写的是"最近 3 个或 8 个格点的平均值"，
但 7 号实测出增益的那一版**没有做平均**：

```
对另外 25 个格点（不含自身），各取两个值：当前 pm2_5、近 3 小时变化
=> 共 50 列，逐列进模型
```

两者的信息量差一个量级：26 个格点压成 1 个标量，等于把所有方向的信息混成一锅；
而 50 列原始值保留了每个格点各自的状态。**按平均值实现，很可能复现不出 7 号那个增益。**

所以 Q3-2 的第②行请按 50 列原始值做。如果因为特征数从 25 跳到 75 影响可解释性，
可以再补一行"压缩版"（最近 k 个均值）作为**对照**，但那是对照，不是主实现。

**Q3-2 的结果已经出来了，而且和预期相反（2026-11-14 补记）：**

| 设置 | Macro-F1 | 高危召回 | 平均代价 |
|---|---|---|---|
| 成对 Top-25（v2 交付版） | **0.7157** | **0.7712** | **0.6369** |
| 加邻域 50 列 | 0.7078 | 0.7319 | 0.6821 |
| 换成"每格点固定一列"排列 | 同样更差 | — | — |

3 种子，不是噪声。3 号还做了排列方式的对照，排除了"按距离排"造成的假象。
**结论：邻域特征只进附录，不进交付特征表，不再迭代。**
理由不是"7 号错了"，而是两件事本来就不同：7 号在 M5 回归设定下测到增益（MAE 5.964 → 5.822），
3 号在默认森林上测到变差，差别在模型与特征压缩方式（75 列时 `max_features='sqrt'` 只给约 8.7 个候选，
受体自身的强特征被稀释）。报告里写"未在分类器上复现"，不写"邻域无效"。

也不要用上风向权重——那是另一套东西（`upwind_pm25_advection_*`），
混进来就又没法归因了。
